=======================================================================
  COMO PUBLICAR UMA ATUALIZAÇÃO PARA TODOS OS PROFESSORES
=======================================================================

Este arquivo é para QUEM MANTÉM o programa (você), não para os
professores que só usam.


-----------------------------------------------------------------------
A ROTINA INTEIRA, EM DOIS PASSOS
-----------------------------------------------------------------------

    1. Suba os arquivos corrigidos aqui no GitHub.

    2. No mesmo envio, mande também:
         - VERSAO.txt    com o número aumentado
         - NOVIDADES.md  com uma seção nova explicando o que mudou

Só isso. Você não precisa apertar botão nenhum.


-----------------------------------------------------------------------
COMO ESCREVER AS NOVIDADES
-----------------------------------------------------------------------

O NOVIDADES.md é o que cada professor LÊ quando o programa avisa que
saiu versão nova. O texto da seção da versão vai inteiro para dentro
daquela caixinha.

Formato (o número tem que ser igual ao do VERSAO.txt):

    ## 1.3.1

    - Corrigido o erro ao registrar aula de Educação Física.
    - A lista de aulas agora mostra também as de sexta-feira.

Escreva pensando em quem vai ler ali: o professor quer saber o que muda
para ELE, não o nome do arquivo que você alterou.

Se você esquecer de criar a seção, a nota vira o texto do commit — que
costuma ser algo como "Add files via upload", e não ajuda ninguém.


-----------------------------------------------------------------------
O QUE ACONTECE SOZINHO
-----------------------------------------------------------------------

O GitHub confere o repositório assim que algo muda E, por garantia, de
15 em 15 minutos. Quando o número do VERSAO.txt ainda não tem release,
ele:

  1. empresta um computador com Windows;
  2. monta o Registro-SED.exe com o código novo;
  3. confere se o executável saiu inteiro (se não saiu, PARA e não
     publica — ninguém recebe versão quebrada);
  4. publica em "Releases" com as suas notas;
  5. atualiza o versao.json, que é o que avisa os professores.

Quando o número JÁ tem release, a execução termina em segundos sem
fazer nada. É por isso que ela pode rodar de 15 em 15 minutos sem
incomodar: publicar é aumentar o número do VERSAO.txt, e mais nada.

Você acompanha na aba "Actions": bolinha amarela = montando, verde =
publicado, vermelha = deu problema (clique nela para ver em que passo
parou).

Se um dia precisar republicar o MESMO número (por exemplo, o build
falhou por causa da internet do GitHub), vá em Actions > Montar o
programa > Run workflow e marque a caixinha "Publicar de novo mesmo que
a versão já exista".


-----------------------------------------------------------------------
ONDE FICA A CONFIGURAÇÃO DO BUILD (IMPORTANTE)
-----------------------------------------------------------------------

Quem manda de verdade em como o .exe é montado (ícone, compressão UPX,
metadados de versão, quais arquivos entram) é o passo "Montar o
executável" dentro de `.github/workflows/montar-programa.yml` — a linha
de comando do PyInstaller ali.

O `Registro-SED.spec` que existe na pasta é IGNORADO pelo Git
(`*.spec` no `.gitignore`) e o robô NUNCA o lê — ele só existe para
testar uma montagem localmente antes de publicar, com as MESMAS flags
do `.yml`, e é reescrito do zero toda vez que você roda `pyinstaller`
com parâmetros na linha de comando (então não adianta comentar nele,
o comentário some no próximo build).

Ou seja: se um dia precisar mudar como o programa é montado, mude no
`.yml` — mudar só o `.spec` local não afeta o que os professores
recebem.


-----------------------------------------------------------------------
A REGRA DO NÚMERO DA VERSÃO
-----------------------------------------------------------------------

    1.3.0  ->  1.3.1     correção pequena
    1.3.0  ->  1.4.0     recurso novo
    1.3.0  ->  2.0.0     mudança grande


-----------------------------------------------------------------------
O QUE A ATUALIZAÇÃO NUNCA TOCA
-----------------------------------------------------------------------

    .env                       (configuração antiga, de quem já tinha)
    configuracao.json          (escola, professores e CPFs)
    browser_profile/           (login do Google da escola)
    registros_enviados.json    (o que já foi enviado à SED)
    aulas_nao_realizadas.json
    ultimo_professor.txt

Quando o programa se troca, o executável antigo fica ao lado como
"Registro-SED.antigo.exe" até a abertura seguinte. Se uma versão sair
com defeito, dá para apagar o novo e renomear esse de volta — e as
versões antigas continuam em "Releases", para baixar de novo.

E o mais importante: publique logo uma versão corrigida, com o número
maior. Ela chega para todo mundo do mesmo jeito.


-----------------------------------------------------------------------
O QUE NUNCA SUBIR PARA CÁ
-----------------------------------------------------------------------

Este repositório é PÚBLICO. Nunca envie:

    .env                    (pode ter CPF e senha)
    configuracao.json       (tem os CPFs dos professores)
    browser_profile/        (tem o login do Google da escola)
    os arquivos .json de histórico

O .gitignore já bloqueia isso para quem usa o Git, MAS a tela de
"Upload files" do site do GitHub não respeita o .gitignore: ali, o que
você arrastar, sobe. Confira o que está selecionando.

Se um dia subir sem querer, não basta apagar o arquivo depois — o
histórico guarda. Nesse caso: troque a senha da agenda na hora e me
chame para limpar o histórico do repositório.


-----------------------------------------------------------------------
E SE O NTE/SED QUISER HOSPEDAR NO SERVIDOR DELES?
-----------------------------------------------------------------------

Funciona igual, sem reescrever nada: eles hospedam os mesmos arquivos
(versao.json + o .exe), e cada professor troca só a linha
URL_ATUALIZACAO do .env para o endereço novo.

Foi feito assim de propósito — o endereço é configuração, não está
gravado dentro do programa.


-----------------------------------------------------------------------
QUANTAS PESSOAS BAIXARAM O PROGRAMA?
-----------------------------------------------------------------------

O GitHub conta sozinho cada download dos arquivos de uma versão
("Release"), e a contagem é pública. Para ver os números por versão,
num terminal, dentro da pasta do programa:

    python contar_downloads.py

Como ler:

    Instalador               novas instalações — o mais perto de
                             "quantas pessoas começaram a usar".
    Portátil + atualizações  quem baixou o portátil, MAIS cada
                             atualização automática (o programa se
                             atualiza baixando esse mesmo arquivo).
                             Numa versão nova, este número sobe com a
                             quantidade de computadores que atualizaram.

O que não dá para saber: "pessoas diferentes". Quem baixa duas vezes
conta duas, o GitHub não diz quem baixou, e quem recebeu o programa por
pen drive ou e-mail não aparece. O selo "downloads" no alto da página do
repositório mostra o total de todas as versões juntas.


-----------------------------------------------------------------------
QUANTOS COMPUTADORES E ESCOLAS ESTÃO USANDO O PROGRAMA?
-----------------------------------------------------------------------

Os downloads do GitHub misturam os seus testes com os dos professores.
Por isso, a partir da versão 2.1.0 o programa avisa o servidor da escola,
no máximo uma vez por dia e em segundo plano, que está sendo usado. Para
ver os números, num terminal, dentro da pasta do programa:

    python contar_usuarios.py

(ou abra https://registro-sed-ia-plexe1.vercel.app/api/uso no navegador;
são só números).

O que o aviso leva: um número aleatório da instalação, a versão do
programa e (a partir da 2.3.0) a escola escolhida no cadastro, mas só se
for igual a um nome da lista oficial (escolas.py). Nada de nome de
professor, CPF, aulas ou do que se escreve na IA. O servidor não grava o
IP e não guarda os números dos computadores de um jeito que dê para
listá-los: só conta quantos são diferentes (com cerca de 1% de erro).

Quais ESCOLAS usam: o endereço de totais mostra só quantas escolas
diferentes. Os NOMES só abrem com a senha do painel (variável PAINEL_TOKEN
na Vercel), que fica só no seu computador, no arquivo painel_token.txt da
pasta %APPDATA%\RegistroSED (ou na variável REGISTRO_SED_PAINEL_TOKEN) —
nunca no repositório. Com ela, "python contar_usuarios.py" mostra também
quais escolas já usam (computadores e último dia) e quais ainda não
apareceram.

Como ler:

    - É contagem de COMPUTADORES, não de pessoas: dois professores no
      mesmo computador contam uma vez; quem reinstala ou apaga a pasta de
      dados conta de novo; computadores que se restauram sozinhos ao
      reiniciar podem contar de novo a cada dia.
    - Só aparece quem já atualizou para a 2.1.0 ou mais nova (e a escola,
      para quem atualizou para a 2.3.0). Nos primeiros dias os números
      sobem conforme os professores abrem o programa.

Para tirar um computador da contagem (o seu, por exemplo), crie um
arquivo chamado modo_teste.txt na pasta de dados dele (ao lado do .exe,
ou em C:\ProgramData\RegistroSED quando instalado). Faça isso ANTES de
abrir a versão nova nesse computador. A variável de ambiente
REGISTRO_SED_NAO_CONTAR=1 faz o mesmo.

Quem mantém precisa, uma vez, ligar o Redis gratuito da Upstash ao
projeto da Vercel (variáveis KV_REST_API_URL e KV_REST_API_TOKEN) — ver
o README da pasta servidor-ia/.
